How to read the trust ratings

Where each statement comes from

Every statement in a review map has one of three origins. The ratings on this page count how much of each answer rests on the stronger kinds.

Computed

Copied from the recorded runs by a script: test outcomes, coverage, the values at each hand-off. The reviewing agent cannot word these.

Gated

Words written by the reviewer, where every cited run, test or code line was looked up by the script and quoted next to the words. A pointer that doesn't hold moves the item out.

Stated

Prose nothing checks: the reviewer's explanation, or a number typed inside a sentence. Read it as opinion.

Ask 1

The concept: run the change, show the evidence, leave the decisions to a named human

“Define the concept: what your team recommends the PR review factory should follow.”

Review-map treats a pull request as a change to a pipeline, not a pile of lines. A reviewing agent that did not write the change picks real inputs. Those inputs run through the real pipeline twice, on the code before and after the change, and every hand-off between stages is recorded. The human then reads three short lists and the evidence behind them, instead of every line.

Step 1 · planChoose inputs

The agent reads the diff and the issue, splits the issue into requirements, picks inputs and predicts how the bug will show.

Step 2 · evidenceRun before and after

Each input goes through the real generator, analyzer and serializer on both sides, plus the repo's tests with coverage.

Step 3 · analyzeExplain with pointers

The agent writes findings, decisions and gaps, each pointing at a run, a test or a code line. A script checks every pointer.

Step 4 · postOne PR comment

Found, refused to decide, not checked, then the requirement table, the pipeline map and one trace per input.

The answer to “is line-by-line review still right?”: for agent-written changes, mostly no. What a reviewer needs is what each unit receives and emits, and which change causes which effect, shown with real data. Line reading is kept for the few hunks the evidence cannot settle.

Trust: high for the concept, partial coverageBuilt and run

The full pipeline runs in GitHub Actions on the fork and posted PR 2's review automatically. PR 1's review uses the same runs and gate, but its write-up was done by hand (see Ask 3). Branches 2129 and 2297, the two larger changes, have not been reviewed, so the concept is untested on a 237-file change.

Ask 3

The reference: PR 1, requirement MessagePack-CSharp#2283

“Illustrate it as a reference, on one sample agent-written change with its requirement ID.”

The change

One agent-written commit on ju26-issue-2283, 4 files. The issue: the MessagePack source generator and analyzer crash with IndexOutOfRangeException when a member's type is a closed generic struct from a referenced assembly.

The PR does two things: two null-safe lookups (the crash fix), and a new filter that drops every diagnostic located outside the project being compiled.

What was run

  • 4 inputs: the issue's repro, a referenced generic struct and a referenced generic class with an unkeyed member, and the same type declared in-project as a control.
  • Each input on the code before and after the PR, and on 4 more builds of the PR with one part removed (lines 239, 985, 1077, and the filter group).
  • MessagePack.SourceGenerator.Tests on both sides, with code coverage on the after side.
  • The known-break run on all 4 inputs.

Technology, by layer

Frontend

One GitHub PR comment in plain Markdown: Mermaid diagrams for the pipeline and each input's trace, folded tables for the full values, links into the code at the reviewed commit. Nothing to install for the reader.

Backend

GitHub Actions with three jobs. Node orchestrates; an xUnit probe drives Roslyn and the serializer; Claude (Sonnet 5.5 by default) via structured outputs; a repo adapter holds everything specific to MessagePack.

Security

PR code runs only in the job without the API key; the reviewer comes from the base branch, so a PR cannot change its own reviewer; the comment never links upstream issues and only mentions people a human named.

Trust: medium-highRuns2 caveats

The recordings are real and reproducible: re-running the evidence matched the earlier recording at every hand-off. Two things lower the rating. First, PR 1's write-up was done by hand, then put through the same gate and rules as the automated path; its requirements were written after the runs, so they are not a prediction, and the comment says so. Second, the runs used .NET SDK 9.0.301 while the repo pins 8.0.402; the comment shows this as reduced confidence at the top.

Ask 6

Failure modes seen, and the decision log

“Name the failure modes you saw, and keep a short log of decisions.”

In the agent-written change (PR 1)

  • Scope creep. A reporting-policy change rode along with a 2-line crash fix; the what-if run shows they are separable.
  • A test that locks in a side effect. The third new test asserts the silenced error as the expected result.
  • New behaviour documented as old. MsgPack004.md describes “only reports on members declared in the project” as if it had always been so.
  • A half-true justification. The code comment says reporting a location-less diagnostic is not permitted; before the PR it was reported and accepted.

In the AI reviewer itself

  • Claimed evidence that wasn't there. An early gate accepted any pointer containing “170 tests passed”. Replaced by resolved pointers.
  • Gaming the symptom. On PR 2 the agent predicted the crash the PR fixes as “the bug”. Partly closed: “fixed” now also needs the symptom gone after.
  • Environment drift. PR 1 ran on SDK 9 against a pinned 8; a later bug read the SDK version outside the repo and raised a false alarm.
  • A stale reviewer. CI once used an old copy of the reviewer from the PR's recorded base commit; now it takes the base branch tip.
  • An overstated write-up. Our own hand-written analysis of PR 1 called both lookups “the crash fix”. The per-line builds showed only line 1077 is; line 985 changes nothing any input shows.

What review-map missed on PR 1

A second team's reviewer, run on the same branch, reported three things review-map did not. They are listed as reported, not yet confirmed by a run here.

  • A positional record with [property: Key(null)] may silently lose its MsgPack005 error under the new filter.
  • The filter drops every location-less diagnostic, not only MsgPack004, for example a missing deserializing constructor.
  • The base branch carries a Roslyn version bump inside a commit titled “Bump PolySharp”, which a reviewer could mistake for part of the change.

The first two are exactly what new probe inputs can settle; adding them is the next step.
